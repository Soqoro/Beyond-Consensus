# Beyond Consensus — Phase II protocol, audited revision

**Version:** 3.0, 26 October 2026  
**Status:** Research design and local implementation specification, not authority to run models, download data, spend money, or submit jobs.  
**Precedence:** This complete protocol and PILOT_MANIFEST_V3.yaml supersede v1 and v2 for the next Codex handoff. The audited manuscript and released Phase I results are unchanged. New design decisions below are proposals/amendments, not completed results. The immediate task remains local CPU/mock implementation; no real experiment is authorised.

**Reading guide:** The central scientific changes in v3 are fixed allocation identities across execution repetitions, a size-covering development pilot, paired common-coverage cost analysis, explicit unknown outcomes, and precise interrupted-execution repair semantics. The full change record is in PLANNING_AUDIT_V3.md.

## 1. Scientific target and retained scope

Test whether recovery-aware ownership, selected using prospective heterogeneous operation-cost estimates, reduces measured reconstruction expenditure on fixed complementary LLM workflows. Do not mistake exact optimisation of a supplied cost table for an empirical token-saving result.

The primary comparison retains one or two predefined tasks per active agent, exactly n active agents, n <= m <= 2n, and n in {4,5,6,7,8,9,10}. All allocators receive identical tasks, dependencies, required outputs, cost estimates, worker capabilities, and repair policy. Mean-first and worst-first are separate lexicographic objectives. A graph generated by a different planner creates a different paired comparison unit.

The main algorithm changes ownership, not task boundaries, dependencies, model choice, or communication protocol. The n=2–4 exhaustive records remain immutable; completing n=5–7 enumeration is a separately authorised track, not a dependency of this implementation. No RL training or general A×B×C optimality claim is added.

### Experimental questions

1. Does the integrated exact solver reproduce source-bound and independent small-instance optima and operate at n=4–10?
2. Do prospective cost-aware allocations reduce measured repair expenditure relative to objective-matched LLM and heuristic allocations, subject to restoration-quality checks?
3. Where do cost drift, undeclared dependencies, failed execution, or adversarial corruption limit the model's predictions?

## 2. What an owner means in this experiment

An owner is a persistent **logical trust/fault domain** for its assigned tasks. Each task retains its own prompt, inputs, tool permissions, and output schema. Its execution context contains only its specification, allowlisted immutable inputs, and declared parent artifacts. Ownership controls attribution and which outputs become untrusted together; it must not silently add cross-task memory.

The same model service may serve all owners, but the injected compromise targets one owner's output boundary only. Do not change the shared model checkpoint, service-wide system prompt, global cache, or evaluator and describe the outcome as a single-owner compromise. This is an owner-scoped output-integrity threat model, not a weight-backdoor or whole-process compromise study. Later stateful or heterogeneous-agent variants are explicitly outside the primary theorem regime.

Tasks may resume under an owner after other owners have acted. A cyclic owner-contracted graph is not evidence that the task DAG is cyclic. Scheduling is at task level; use a stable task-ID topological order for the controlled tier. Latency/parallel scheduling are secondary and must not alter that tier's cost comparison unnoticed.

Planner, scheduler, accounting, injector, and outcome evaluator are protected infrastructure. Any model call that produces required workflow content, including final synthesis or an internal critic, is represented as a task and has an owner. An external evaluator never supplies corrections to the workflow. Trusted replacement workers use the same model snapshot and task policies, with the compromised output intervention removed.

## 3. Workload construction and admissible sizes

Freeze distinct, meaningful task deliverables before allocation. Define required outputs O and verify that every workload operation is required either directly or as an ancestor of O. Reject padding, duplicate whole-question solutions followed by voting, hidden shared state, undeclared reads, and unused optional branches. Do not silently prune or add operations after allocating tasks.

Structural reachability does not establish semantic necessity. Use a content-based admission rubric before viewing allocator performance, and a prespecified artifact audit on development/test samples. Every declared parent must be supplied and its read recorded. A read proves exposure, not actual semantic dependence; state that boundary. Do not give every worker unrestricted source access that lets it bypass the intended complementary work without recording the adaptation. Global problem text, when necessary, is an explicit input; gold solutions never are.

Use each graph only for max(4, ceil(m/2)) <= n <= min(10,m). No single m supports all n=4–10. Assign a primary n by source-level stratification before method outcomes, and use a preselected within-graph n sweep as sensitivity analysis. m=n is a no-choice control. In particular, nontrivial n=4 comparisons need m in {5,6,7,8}; n=10 needs m in {11,...,20}. Do not pad small problems to satisfy coverage.

All attempted decompositions and rejection reasons remain in a screening ledger. One proposal plus one structural correction is the starting planner allowance. Invalid plans are not repeatedly regenerated until convenient.

## 4. Data, evaluators, and leakage

Retain the proposed starting domains: MATH-500, an explicitly selected GPQA release/subset, and accessible GAIA validation items with resettable resources. These are adapted complementary-workflow evaluations, not official full-benchmark scores. ARC-100 remains disabled until its intended identity is supplied. MultiAgentBench/MARBLE remains an optional later extension; do not build every adapter now.

Split by original source problem before fitting cost estimators or tuning prompts. Maintain cross-release GPQA and source-family duplicate checks. Hold out all test-derived task prompts, artifacts, token bills, labels, and recovery logs from estimator fitting. Public model-training contamination cannot be ruled out by this split.

Use an allowlist transformation from raw dataset records to worker inputs, not a blacklist. MATH solutions/answers remain evaluator-only. GPQA answer texts become neutrally named choices with a deterministic source-level permutation; field names such as `Correct Answer`, explanations, and the answer-position mapping are private. Freeze the same permutation across methods. GAIA answers/annotated steps stay private; preserve access/redistribution restrictions and do not put raw gated data in public fixtures.

Final-answer validity, schema validity, and semantic validity of intermediate artifacts are different fields. A final correct choice does not prove every required artifact was restored. Use deterministic evaluators where available and separately labelled blinded audits where they are not. Ambiguous grading is reported, not silently marked correct. Test/evaluator feedback is not a retry signal to workers or planners.

The provisional 24-development/60-test-source plan is retained as a budgeting target only. Final N, repetitions, and quality margins are chosen from development uncertainty and budget before test execution. Screening enough valid ten-agent workflows is an empirical feasibility issue, not an assumed property of these datasets.

A four-agent-only pilot does not qualify replay-cost estimation, payload size or failure behaviour on the larger workloads in the main study. Keep the initial three-workflow smoke test at n=4. Reassign the subsequent 12-workflow development pilot to a provisional 4/4/4 split at n=4,7,10, using meaningful eligible graphs (m>n). These are size-coverage targets, not a demand that every domain supply padded workloads. Development calibration must include examples of the larger task/closure/context sizes or explicitly report them as unsupported. Pilot eligibility and allocation do not depend on optimiser gains. When coverage or funding is insufficient, narrow the main scope or request a documented pre-test amendment; do not claim that a small-workflow pilot validated the entire range.

## 5. Allocators and ablations

Retain eight outputs in the main comparison:

- one seeded random valid allocation;
- one direct-workload minimax allocation;
- recovery-aware local search for mean-first and worst-first;
- LLM allocation for mean-first and worst-first;
- exact matching for mean-first and worst-first.

All outputs have m-n pairs and 2n-m singletons. A uniform random partition can be sampled by uniformly permuting the real tasks, pairing the first 2(m-n), and making the rest singletons, then discarding ordering within/between groups. This has equal multiplicity for each unlabelled feasible partition. Random edge weights in matching are not a replacement for this sampler.

Direct-workload balancing minimises the maximum sum of **owned tasks' estimated replay costs**, not recovery closures. Its total direct load is constant; use a stable tie rule independent of downstream recovery information. This is an own-work-replay balancing ablation, not measured clean-execution or latency balancing unless separate forward-cost inputs are supplied. Compute the minimum bottleneck using matching on singleton/pair sums; do not substitute a greedy routine and label it optimal. The recovery-aware local search starts from the random control, accepts the best strict objective improvement from valid pair-to-singleton transfers and intergroup exchanges, and stops after 20 accepted moves or no improvement. No exact-solver fallback.

Give the LLM baseline the same objective and the complete precomputed singleton/pair recovery-score table, as well as the task descriptions and DAG. These scores reveal no optimal assignment. Freeze inference/correction budgets, record invalid results, and never repair an LLM plan with our optimiser while labelling it LLM-only. Original legacy planner outputs that violate the cap are a separate descriptive condition, not a same-feasible-set baseline.

The unit-cost ablation was specified in v1.0 but absent from its run matrix. Add two explicit outputs, matching_mean_unit and matching_worst_unit, on a source-problem subset chosen before method outcomes. Evaluate their assignments using the same measured heterogeneous executor costs; do not execute a fictional unit-price LLM. Budget this subset separately. It need not double the full grid. Predicted-gain selection is prohibited.

### Fixed allocations, repetitions and identity

Create each allocation once per (workflow, n, estimator, method, allocation seed) and commit its canonical task-group partition before any evaluation execution. Execution repetitions reuse that exact partition. Freeze random draws, the LLM allocation response, matching tie resolution, and local-search output; do not replan separately for each execution replicate. A new cost estimate or partition is a new allocation condition, not an extra repetition of the old one.

Define an owner by the sorted IDs of its member tasks within an allocation; arbitrary names such as agent_0 are not identities across runs. Define a stable allocation digest, incident-group digest, clean-trace ID and execution-repetition ID. The same source/graph/method/seed condition cannot silently contain multiple partitions. Do not align owner labels across different methods.

For an optional future allocation-seed study, retain a separate index k. First compute the worst-owner statistic for each fixed P_k, then summarise over k. Averaging the costs of differently assigned agent_0 values before taking the maximum estimates a different quantity. The current campaign uses one frozen allocation draw per method/condition, so inference is conditional on these draws; no claim of integrating over all stochastic planner outputs is made.

## 6. Cost estimation and calibration without a circular gate

Choose one primary additive cost unit per executor. Profile replay expense on development tasks and incident contexts; a task replayed repeatedly within one graph is not an independent training source. Use source-balanced fitting and source-disjoint validation, or cross-fitting within development. Features must be available before allocation: do not use future realised parent lengths or the evaluated clean/recovery bill.

A simple type/length estimator is sufficient initially. Unknown types receive a recorded positive fallback estimated from development, not an invented bound. Predicted rational weights can be exact decimal/integer-unit representations; exact matching then optimises those represented estimates, not the unknown true expectations.

Calibration precedes a fitted estimator. The default collection allocation is a frozen uniform random allocation, with owner sweeps specified before observing costs. A direct-cost collection allocation requires an already declared ex-ante cost source; otherwise it recreates a calibration dependency. Profile a range of eligible graph sizes and closure sizes. It needs approved models, data, evaluator, resource limits, and a collection policy, but not an already fitted estimator or final main-test power calculation. Pilot comparisons require a frozen development estimator per batch. Main tests require the final estimator, sampling, analysis, and budgets to be frozen. No stage uses test feedback to improve cost prediction.

An independent per-instance profiling condition is optional. Charge it and share it across methods. Cold-start versus amortised accounting must be explicit. Never enable profiling of the evaluated incident and call it prospective optimisation.

## 7. Controlled clean execution and genuine replay

### Shared clean trace amendment

In the strict task-isolated tier, ownership does not appear in task model payloads, tool permissions, sampling configuration, or execution order. After all allocations and estimates are committed, one complete clean trace per workflow/executor/repetition may serve as the common baseline for its allocation comparisons. Preserve immutable task-level provenance and add separate ownership-binding views; do not rewrite the original trace to change its attributed owner.

Enable this only after a payload/read-contract invariance test, and log external execution conditions that cannot be controlled. Distinguish state independence from random-number independence. Shared-clean mock streams use workflow/executor/task/repetition identity. Repair mock streams additionally include the canonical allocation and compromised task group, phase and attempt; different incidents and repetitions must not accidentally reuse one stream. Sham/attack coupling may deliberately use common worker randomness only under a declared pairing policy. Never key identity by arbitrary owner names or execution order. Provider seed support does not prove deterministic execution or statistical independence; record what is actually supported. Shared clean execution is a variance-control and research-cost reuse, not evidence that independent runs are identical. Report the intended task-isolated setting rather than a broad owner-state quality claim.

If payload/order invariance fails, require a new documented protocol with method-specific clean runs; do not silently downgrade. Physical clean-trace reuse conditions the comparison on the same baseline artifacts; it is not evidence of equal realised outcomes under independent deployments. State-sharing sensitivity belongs in a separate external-validity tier. No affected-task repair outputs are shared merely because a clean trace is shared. Identical full partitions may share an actual execution under an explicitly recorded deduplication key; shared observations are not new replications.

### Invalidation/replay condition

For each allocation P and owner i, compute D_i from all of i's tasks plus their descendants. Fork the complete clean artifact snapshot anew. Remove all D_i artifacts and associated stale context, preserve only trusted artifacts outside D_i, and physically re-execute D_i in task-DAG order. Affected tasks cannot read original clean outputs through cache or file paths. Content hashes returning identical results do not establish caching; retain invocation records.

Evaluate the repaired required outputs. If the clean graph did not complete, there is no complete-work reconstruction trial: preserve planned slots as `no_clean_snapshot` and report coverage. A complete but semantically wrong clean trace is retained with its validity flag; repair costs can be measured, but turning it correct is not labelled restoration from a previously correct run. Predeclare a common-clean-valid conditional analysis alongside all planned workflow outcomes.

## 8. Actual corruption, sham branches, and terminal tasks

Actual corruption is a separate study, not another name for invalidation. Fork immediately before the target owner's first task in the fixed topological schedule. Corrupt emitted artifacts only for that owner, and execute the remaining consumers on those artifacts. The injector has no access to hidden labels or protected scheduler/evaluator state.

Use an unchanged-output sham branch from the same checkpoint and a matched execution policy. A full clean baseline is an acceptable sham reuse only if its prefix, payloads, RNG policy, tool state, and generation conditions actually match; otherwise run a fresh sham and charge it. With stochastic generation, do not claim that every observed pre-repair error was caused by the attack. Report paired validity changes and uncertainty.

Use plausible incorrect-content and goal-deviating-content families later, with a fixed total attacker budget per owner incident plus per-task limits. Allocate opportunities deterministically across the owner's one or two tasks. Changing output count may be a property of the organisation; do not additionally give two-task owners twice the total adversarial-model spend unless that is a separately specified threat regime. No attack-until-success loops.

Record application, attempted/direct-output or downstream exposure, sham/attacked pre-repair validity, and post-repair validity. A terminal owner can corrupt the required final output without any descendant; `downstream_consumption` is then not applicable, not an exclusion or invalid attack. An internal perturbation with no observed read has zero recorded downstream exposure and remains in the denominator.

Oracle detection occurs at completion or a prespecified terminal failure/resource limit, never only after a successful attack. Revoke the target intervention and use fresh trusted workers for repair. Compute the conservative invalidation closure D_i from the entire owner task group, not only successfully changed outputs.

For an interrupted attacked execution, let E be tasks with schema-valid committed artifacts at detection (semantic correctness is separate). Preserve E\D_i. The trusted scheduler must execute U=D_i union (V\E), in task order: previously completed affected tasks D_i intersect E are reconstruction, and all missing tasks V\E are completion work, including missing tasks outside the compromised closure. A previous failed attempt without a committed artifact does not make a task complete. Charge previous attempts and new completion separately. When E=V this reduces to ordinary reconstruction. Otherwise U's cost is not the completed-trace theorem's recovery objective. Test an example where missing unaffected tasks would be omitted by replaying D_i alone.

## 9. Outcomes, censoring, and inferential claims

Keep separate fields for logical status, every observed spend component, complete replay cost, validity, attempted tasks, completed tasks, and missing usage. Suggested terminal categories include complete_valid, complete_invalid, task_error, schema_failure, resource_stopped, infrastructure_failure, no_clean_snapshot, invalid_allocation, and protocol_violation. Separate status axes are preferable where more than one applies.

A completed but wrong reconstruction has a measured full execution cost and failed validity. A repair stopped after only part of D_i has an observed attempted spend but an unknown complete-reconstruction cost. Do not substitute the partial bill, zero, infinity, or an unrelated cap into that missing cost. Incomplete usage is also unknown, not zero. Retain all trial slots and failure denominators.

For a workflow/allocation with a complete balanced S-by-n matrix of full costs r_i,s:

    owner_mean_i = sum_s r_i,s / S
    mean_repair = mean_i owner_mean_i
    worst_owner_mean_plugin = max_i owner_mean_i
    observed_max = max_i,s r_i,s

When the matrix is incomplete, flag the full-cost summary as incomplete; available-case values are diagnostics, not primary replacements. For an objective-matched pair of methods, any complete-cost comparison uses the intersection of source conditions with complete matrices for BOTH methods. Fix source weights in advance and report exclusions, coverage and failure types per method. This is conditional complete-case evidence, not an unbiased estimate of costs on the entire intended population when missingness depends on outcomes. Never compare each method's separately completed subset. Keep the all-planned outcome table and do not make a blanket savings claim from selective complete cases.

Use independent outcome axes: execution/coverage status; schema status; semantic validity {valid, invalid, unknown}; accounting {complete, pending, missing}; and budget {within, exceeded, unknown, not_applicable}. Missing metering or grading is not a pass. Nor should an absent evaluation be silently converted into a semantic error. A real resource stop after starting differs from not_run_due_campaign_stop, invalid_allocation, or no_clean_snapshot. All retain planned slots and reasons. A complete wrong output has a full cost but failed restoration; an unstarted trial has no realised recovery cost.

Define measured successful-restoration-within-budget for a fixed attempt only when completion, selected quality checks and the relevant cost unit are known: valid completed restoration with measured full spend <=b passes; an explicitly failed/stopped attempted restoration or known expenditure >b fails; unresolved execution/grade/usage is unknown unless failure is already established; unstarted cases remain explicitly unobserved. For the all-planned endpoint, report proven successes, proven failures, unobserved/unknown cases, and counts attributable to invalid plans, rather than one silently imputed success rate. Invalid allocations are known nondeployments for intention-to-plan success, not zero-cost repairs. Simple identification bounds [passes/N,(passes+unknown)/N] may be reported for a precisely defined denominator, but are not confidence intervals. Show valid-plan and executed-trial coverage separately. Compute rates/bounds within a workflow/allocation and aggregate with the frozen source/domain weights; pooled incident counts alone do not define the equal-source primary endpoint. The theorem's model budget B and reporting threshold b need not be the same concept.

If full-cost inference is obstructed by censoring, use a prespecified joint cost/quality or bounded-budget analysis; otherwise report it as inconclusive. Do not silently drop owners and still call the remaining maximum worst-case.

The worst-owner plug-in statistic is noisy and potentially upward biased. The largest bill and mean of per-repeat maxima estimate different quantities. Pilot uncertainty determines repeats; three is not automatically sufficient. Main inference requires a frozen method that accounts for owner-mean uncertainty and clustering. Do not implement a simple pooled-owner bootstrap as if owners were independent problems.

Primary paired comparisons are ours-mean vs LLM-mean and ours-worst vs LLM-worst. Cluster by original problem, nesting plans, counts, repetitions, and attack families. Equalise source weights within domain and report a prespecified domain aggregate. Freeze multiplicity correction and quality non-inferiority criteria before main execution. A nonsignificant quality difference is not proof of equal quality. Invalid plans are outcome failures, never cheap allocations; include coverage and separate valid-plan comparisons.

## 10. Budgets and execution accounting

Maintain physical research-event costs, one-deployment counterfactual accounting, and operation-reconstruction costs as separate views of the same events. A physically shared clean run is counted once in research spending, but each method's deployment includes one whole clean execution cost, not one eighth of it. Never sum every counterfactual owner's incident bill into one deployment.

The primary optimisation experiment is unbudgeted in the mathematical sense (minimise mean/worst); comparative_run.predicted_incident_budget must be null. Test optional mathematical budget B in the solver's local API, but do not silently apply B to matching alone, use unit-weight ablation scores as money, or let random/greedy/LLM methods use a different feasible set. A budget-constrained comparative experiment requires a separate specification for objective weights, common heterogeneous constraint weights, rejection/repair policies, and fair baseline treatment. Reporting measured restoration under predeclared expenditure thresholds is still allowed and does not constrain the allocations. Mandatory campaign/task safety caps always apply and must not be confused with B. With estimated weights, solver B-feasibility is model feasibility, not a hard guarantee about realised bills.

Freeze an order for logical trial slots before evaluation: balance/interleave objective-matched methods and randomise owner order using an independent scheduling seed. Stable task order applies inside an execution, not to always running one method first. Do not schedule by predicted savings, price, successful outcomes, or remaining-budget convenience. If the campaign stops, retain every pending slot as not_run_due_campaign_stop. Record block completion and paired coverage; a budget cannot convert a partial sweep into a mean/worst observation. Resume only the same frozen specification; configuration changes form a new condition.

Use idempotent logical-slot and physical-attempt IDs. A retry adds an attempt and its bill; it does not overwrite an earlier failure. No semantic/schema retry-until-success or reallocation is permitted. Any future bounded infrastructure-retry policy is fixed in advance and cannot replenish resource allowances or discard uncertain billed calls.

Use atomic spend reservations before calls if parallelism is later enabled. Reserve a conservative maximum allowed call/tool cost, reconcile reported usage, retain unresolved reservations after ambiguous failures, and count retries. Missing prices, unknown usage, absent approvals, or incompatible versions block further remote execution. Do not claim that a point estimate enforces a hard currency cap. Latency and GPU-seconds are separately measured; concurrent GPU attribution needs a defined policy, not summing overlapping wall clocks.

## 11. Stage-specific implementation and launch gates

**Current Codex deliverable: Stage 0 and mocked execution only.** Reuse project code when correct. Read repository instructions, preserve Phase I, run local CPU tests, and prepare a review bundle. No model inference (local or remote), API calls, downloads, GPU jobs, commits, pushes, or submissions. Missing research raw files create a documented binding gap, not guessed instances.

Later stages require separate authorisation:

1. Calibration: pinned worker/planner if used, admitted development data, evaluators, collection policy, access terms, limits/prices and approval. Does not need an already fitted estimator.
2. Smoke: three admitted development workflows at n=4 only when m=5–8; LLM-mean and matching-mean; one replicate; frozen development estimator. Remote run not authorised by this plan.
3. Pilot: target 12 admitted development workflows, provisionally four at each of n=4,7,10, six allocation outputs and two execution repetitions. The allocation is fixed across those repetitions. This covers workload scale without increasing the number of development sources, but does increase owner-replay cost. If a domain or size band cannot support meaningful eligible work, report the gap; do not pad or silently replace it. No larger run is authorised by this change.
4. Main: provisional 60 held-out problems, eight outputs, balanced eligible counts 4–10, three repeats subject to pilot precision; final sample and analysis freeze required.
5. Unit-cost ablation: prespecified main subset and two unit-weight optimiser outputs, all owners and declared repeats; explicit budget.
6. Corruption: preselected subset, four LLM/optimiser outputs, all owners, two attack families, matched sham controls and fixed owner budgets. Its attack policy is not a prerequisite for clean calibration/smoke.
7. Cross-model/planner or stateful sensitivity: separate amendment; do not form a full Cartesian grid.

All-owner sweeps are mandatory for planned configurations; a campaign cap can halt execution but cannot turn a partial sweep into a complete mean/worst result.
